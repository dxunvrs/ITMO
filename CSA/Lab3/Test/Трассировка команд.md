# Доказательство полноты схемы для архитектуры F32a

Ниже приведена трассировка исполнения **каждой** команды из документации ISA на нашей RTL-схеме стадии Execution (EX). Это доказывает, что нарисованных мультиплексоров, шин и сигналов достаточно для реализации всего процессора.

**Терминология сигналов в таблице:**
* `sel_alu_l`, `sel_alu_r` — выбор левого и правого входов АЛУ.
* `sel_mem` — выбор адреса памяти.
* `sel_ds`, `sel_rs` — выбор входа для стеков данных и возвратов.
* `sel_pc` — выбор входа для счетчика команд (переход или +1).
* `alu_op` — операция АЛУ (`ADD`, `AND`, `XOR`, `PASS_L`, `PASS_R`, `SUB`).
* `shift_t` — операция блока сдвига под АЛУ (сдвиг результата или пропуск `PASS`).
* `shift_a` — операция блока сдвига для регистра A.
* `update_t`, `update_s` — сигналы к Data Stack на перезапись только верхних регистров T и S.
* *Везде подразумевается наличие неявного тактового сигнала `CLK`, по фронту которого защелкиваются данные.*

## 1. Data Movement Instructions

| *Instruction*       | *Синтаксис* | *Настройка MUX, АЛУ и Шифтера*                                   | *Операции с памятью и стеком*                         |
| ------------------- | ----------- | ---------------------------------------------------------------- | ----------------------------------------------------- |
| **Literal**         | `lit <val>` | `sel_ds` = arg                                                   | `push_ds=1`                                           |
| **Fetch from Addr** | `@p <addr>` | `sel_mem` = arg                                                  | `read=1`, `sel_ds` = mem, `push_ds=1`                 |
| **Fetch**           | `@`         | `sel_mem` = a                                                    | `read=1`, `sel_ds` = mem, `push_ds=1`                 |
| **Fetch Plus**      | `@+`        | `sel_mem` = a. `sel_alu_l` = a, `sel_alu_r` = 1, `alu_op` = ADD  | `read=1`, `sel_ds` = mem, `push_ds=1`, `latch_a=1`    |
| **Fetch B**         | `@b`        | `sel_mem` = b                                                    | `read=1`, `sel_ds` = mem, `push_ds=1`                 |
| **Store to Addr**   | `!p <addr>` | `sel_mem` = arg                                                  | `write=1` (шина T идет в память напрямую), `pop_ds=1` |
| **Store**           | `!`         | `sel_mem` = a                                                    | `write=1`, `pop_ds=1`                                 |
| **Store Plus**      | `!+`        | `sel_mem` = a. `sel_alu_l` = a, `sel_alu_r` = 1, `alu_op` = ADD  | `write=1`, `pop_ds=1`, `latch_a=1`                    |
| **Store B**         | `!b`        | `sel_mem` = b                                                    | `write=1`, `pop_ds=1`                                 |
| **A-Store**         | `a!`        | Шина T напрямую идет ко входу A.                                 | `latch_a=1`, `pop_ds=1`                               |
| **B-Store**         | `b!`        | Шина T напрямую идет ко входу B.                                 | `latch_b=1`, `pop_ds=1`                               |
| **A-Fetch**         | `a`         | `sel_alu_l` = a, `alu_op` = PASS_L, `shift_t` = PASS, `sel_ds` = alu_result | `push_ds=1`                               |

## 7. Ответы на типовые вопросы к защите схемы (Pipeline-2)

1. **Запишите RTL-шаги выполнения NOP:** 
   Так как у нас конвейер, одновременно (параллельно) работают 2 стадии:
   * *IF (Instruction Fetch):* `IR <- IMEM[PC]`, `PC_next <- PC + 1`, `PC <- PC + 1` (по фронту `CLK`)
   * *EX (Execute):* Нет операций. Control Unit не выставляет сигналы записи, состояние процессора не меняется.

2. **Запишите RTL-шаги выполнения JMP (`<label> ;`):**
   * *IF:* `IR <- IMEM[PC]`, `PC_next <- PC + 1`, `PC <- PC + 1` (инерционное чтение следующей команды).
   * *EX:* На стадии EX анализируется код JMP из текущего `IR`. CU выставляет `sel_pc = jmp_addr` и `flush = 1`.
   * *В конце такта:* В `PC` защелкивается `jmp_addr`, а ошибочно прочитанная на стадии IF инструкция затирается нулями (`NOP`) в `IR`.

3. **Запишите RTL-шаги выполнения ADD (`+`):**
   * *IF:* `IR <- IMEM[PC]`, `PC_next <- PC + 1`, `PC <- PC + 1`
   * *EX:* `T <- T + S + Carry; DS.pop()` (с учетом флага EAM).
   * *Путь данных:* Выходы `T` и `S` стека идут на `MUX_ALU_L` и `MUX_ALU_R`. Значения флагов `C` и `EAM` поступают в АЛУ. Результат через `Shifter` (pass) и `MUX_DS` записывается в вершину стека `T` (по сигналу `update_t`). Стек делает `pop_ds`, удаляя использованный `S`.

4. **Как аппаратно работает шаг деления `+/` за один такт?**
   * *Алгоритм ISA:* `S <- S << 1; if A[31] then S[0] <- 1; A <- A << 1; T <- T << 1; if S >= mem[B] then { S <- S - mem[B]; T[0] <- 1 }`
   * *Как это летит по тракту данных:*
     1. В начале такта значения `T`, `S` и `A` сдвигаются влево на 1 бит (с помощью выделенных блоков сдвига `Shifter_T`, `Shifter_S` и `Shifter_A`, которые для этой команды работают ДО АЛУ или в обход его, перекидывая `A[31]` в `S[0]`).
     2. Память читает делитель: `sel_mem = b`, `read = 1`. Делитель по шине `mem` поступает на `MUX_ALU_R`.
     3. На `MUX_ALU_L` поступает сдвинутый `S_shifted`. 
     4. АЛУ делает вычитание (`alu_op = SUB`): `Diff = S_shifted - mem[B]`.
     5. Если `Diff >= 0`, то на шину записи для `S` уходит этот `Diff`, а в младший бит `T_shifted[0]` записывается 1. Если `Diff < 0`, то на шину записи для `S` уходит исходный `S_shifted`.
     6. В конце такта `CLK` защелкивает новые значения: `update_t=1`, `update_s=1`, `latch_a=1`.

5. **Почему нужен MUX перед входом ALU? Что на него подаётся?**
   Мультиплексор нужен, потому что ALU используется разными командами. 
   На `MUX_ALU_L` подается либо `T` (вершина стека), либо регистр `A`. На `MUX_ALU_R` подается `S`, либо данные из памяти (`mem`), либо константы `0` (для `+*`) и `1` (для инкремента A в `@+`).

6. **Откуда Control Unit знает, какую операцию выполнять?**
   CU анализирует код операции (`opcode`), который находится в конвейерном регистре `IR`. Внутри CU дешифратор команд чисто комбинационно выставляет нужные сигналы (`sel_...`, `latch_...`) для текущего такта.

7. **Как работает регистровый файл: сколько портов, что происходит при одновременном чтении и записи?**
   В F32a нет классического регистрового файла, вместо него — регистры A, B и аппаратные стеки. Аппаратный стек данных имеет асинхронные порты чтения `T` и `S` (данные доступны в начале такта EX) и порты записи (обновляют данные по фронту `CLK` в конце такта). В конвейере 2-stage это устраняет проблемы Data Hazards: чтение и запись происходят на одной стадии EX.

8. **Как работает Memory Mapped I/O: как процессор различает обращение к RAM и к устройству?**
   Устройства мапируются в общее адресное пространство. Дешифратор адреса (`Addr Dec`) смотрит на старшие биты адреса. Если они попадают в диапазон ОЗУ, активируется `CS_RAM` (Chip Select RAM). Если в диапазон ввода-вывода — `CS_IO`. Для процессора разницы нет, используются одни и те же команды памяти (`@p`, `!p`). Возврат данных происходит через `MUX_MEM_OUT`.

9. **Есть ли регистры в Control Unit? Чем отличается single-cycle CU от multi-cycle?**
   В нашем конвейерном варианте CU **комбинационный** (без регистров состояний). Регистр состояний (Step Counter) был бы нужен в базовом (не конвейерном) multi-cycle варианте, чтобы разбивать команду на Fetch и Execute в разные такты. В конвейере эти стадии работают параллельно, а микро-шаги `+*` и `+/` реализованы аппаратно, поэтому машина состояний внутри CU не нужна.

10. **Как отличается схема для Harvard от von Neumann?**
    В гарвардской архитектуре (как на нашей схеме) физически разделены память команд (`IMEM`) и память данных (`DMEM`) с отдельными шинами. Это позволяет конвейеру идеально работать: IF читает инструкции, а EX читает/пишет данные **одновременно**. В архитектуре фон Неймана шина общая, что вызвало бы Structural Hazard (конфликт за шину) при попытке одновременного доступа.

11. **Что хранится в MAR и MDR? Зачем они нужны при multi-cycle?**
    MAR (Memory Address Register) и MDR (Memory Data Register) буферизируют адрес и данные для обмена с общей памятью. В нашей гарвардской конвейерной архитектуре роль MAR для инструкций играет `PC`, а для данных роль буфера играет сам конвейерный барьер `IR` / `PC_next`. Отдельные MAR/MDR не нужны, так как шины разделены.

12. **Покажите на схеме, как выполняется условный переход (BEQ / JZ и т.п.)**
    Значение `T` (вершина стека) подается на блок Flags, формируется сигнал `Z` (`T==0`). Этот сигнал идет в CU на стадии EX. Если `Z == 1` и сейчас выполняется `if <label>`, CU генерирует сигналы `sel_pc = jmp_addr` и `flush = 1`, чтобы затереть неверно предсказанную инструкцию в стадии IF. Если `Z == 0`, конвейер просто продолжает работу.

13. **Как добавить на схеме поддержку стека (PUSH/POP)? Что нужно изменить?**
    В архитектуре F32a стек аппаратный, поэтому логика `PUSH/POP` скрыта внутри контроллера самого стека, а наружу выведены только управляющие сигналы `push_ds`, `pop_ds`, `update_t`. В классической архитектуре (фон Неймана) пришлось бы добавить регистр `SP` (Stack Pointer), подать его на `MUX_ADDR` и пропускать через АЛУ для вычисления `SP +/- 1` при каждой операции со стеком.
